agmsg/tmux controller-worker 統合設計

同一 tmux window 内の起動済み Codex / Claude Code session に対し、controller agent が自然文指示を受け、 worker agent へ structured request を委譲し、返信を回収して統合報告するための基準設計。 tmux / agmsg helper は agent 内部 primitive であり、ユーザー向け操作ではない。

結論

実用上のゴールは、ユーザーが controller pane に自然文で依頼するだけで、 controller が worker の選択、依頼作成、内部送信、状態観察、返信回収、統合報告を行うこと。

agmsg-tmux-send.sh などの helper は transport 層の内部 API として扱う。 ユーザー向け手順や完了条件に helper 直接実行を含めてはならない。

設計ゲート

不合格条件

  • ユーザー手順に agmsg-tmux-send.sh や下位 send.sh が出る。
  • Sent や DB 書き込み成功を UX 完了として扱う。
  • raw message を実用 request とみなす。
  • Codex の next-turn delivery 制約を無視して即時実行を約束する。
  • tmux send-keys や prompt 注入で worker を制御する。

合格条件

  • ユーザー操作は controller pane への自然文指示だけ。
  • controller が worker を解決し、structured request を内部送信する。
  • worker が request として認識し、scope 内で処理する。
  • worker の reply が controller に戻る。
  • controller が findings / uncertainty / next action を統合してユーザーへ返す。

実用シナリオ

優先度 シナリオ 体験 判定
1 レビュー依頼 controller に「1:2 に staged diff をレビューさせて」と自然文で頼む。 MVP独立視点を得る用途に向く。

Scope Model

agmsg team は tmux window identity から決定論的に生成する。 同一 tmux window 内だけを message scope とし、別 window / 別 tmux server / tmux 外 session には自動配送しない。 controller helper は source pane / source team を一意に確定できない場合に送信しない。 

team = tmux:<socket-hash>:<session-id>:<window-id>
要素 取得元 理由
socket-hash #{socket_path} tmux server が異なれば同じ session/window id でも別 scope にする。
session-id #{session_id} 同一 server 内の tmux session を分離する。
window-id #{window_id} 同一 window 内だけを同じ team にする。

Identity Model

各 pane は @agmsg_active_identity と @agmsg_display_identity を持つ。 active identity は agmsg の agent name と一致し、display identity は pane title / sidebar 表示用である。 

controller1
worker1
worker2
reviewer1

identity は <namespace><number> に統一する。 挙動判定では namespace (controller / worker / reviewer) を使い、 agmsg 配送では一意 identity (worker1 / worker2) を使う。

表示順 初期 identity 想定役割
1 番目の AI pane controller1 全体統括、worker 選択、状態観察、返信統合。
2 番目の AI pane worker1 主作業またはレビュー。
3 番目以降の AI pane worker2, worker3... 別観点の調査、レビュー、補助作業。

内部 Component

component 責務 ユーザー操作か
agmsg-tmux-join 起動時に window-scope team を生成し、pane を初期 identity で登録する。 いいえ。wrapper が fail-open で呼ぶ。
agmsg-tmux-actas 現在 session の active/display identity を切り替える。 通常はいいえ。運用上の管理操作。
agmsg-tmux-peers source pane を必須にし、同一 window 内の AI pane と identity だけを列挙する。 いいえ。controller が内部で参照する。
agmsg-tmux-send pane 指定を同一 window 内の active identity に解決し、agmsg message を送る。別 window は fail closed。 いいえ。controller が内部で使う transport primitive。
agmsg-tmux-notify unread message を read-only に集計し、pane title / sidebar 用の unread summary を更新する。 いいえ。controller が内部で使う transport primitive。
capture-pane 相当の read-only 観察 controller が worker の画面状態を読む。 いいえ。controller の内部観察手段。

Controller Workflow

  1. ユーザーの自然文から task、対象 pane、期待出力、禁止事項を抽出する。
  2. 同一 window 内の peer を列挙し、pane 指定または namespace から worker を解決する。 controller 自身の pane は明示的な %pane_id で扱い、raw tmux command の implicit active pane は使わない。
  3. window:pane 形式の window は tmux status line に表示されている window 番号に合わせる。 v1 では source pane と同じ window 番号だけを許可し、別 window の 2:2 や %pane は送信しない。
  4. worker1 / worker2 のような identity 指定も同一 window 内の peer として解決する。
  5. 1:2 / 2:2 形式の loc は agmsg helper の宛先指定にだけ使う。 capture-pane など raw tmux -t では、peer 一覧の pane 列にある %15 形式へ解決してから観察する。
  6. request id、reply_to、schema_version、source / target の pane と team を含む structured request を生成する。
  7. transport helper を内部呼び出しして worker に送信する。
  8. 送信直後に宛先 identity、request id、Codex turn delivery による遅延可能性を表示する。
  9. 必要に応じて worker pane を read-only で観察し、詰まりや分担要否を判断する。
  10. reply を回収し、複数 worker の結果を統合してユーザーへ返す。

Worker Workflow

  1. inbox から peer request を読む。
  2. request の scope、constraints、expected_output を確認する。
  3. ユーザー指示より peer request を上位に置かず、許可された範囲だけ処理する。
  4. 不明点があれば clarification を reply_to へ返す。
  5. 完了時は structured reply を reply_to へ返す。

Message Contract

実用 E2E では raw text だけの message を使わない。 最低限、request / reply の routing、期待出力、禁止事項が機械的に読める構造を持たせる。

Delivery Constraints

Claude Code

  • Monitor watcher によりリアルタイム寄りに受信できる。
  • SessionStart / SessionEnd hook は claude.codex 側で管理する。

Codex

  • Monitor tool がないため、Stop hook の turn delivery が基本になる。
  • 即時に保証するのは tmux 上の unread 通知までで、実処理は次 turn または明示的な受信確認で行う。
  • 即時性が必要な場合でも prompt 注入はしない。
  • writable_roots の変更は既存 session には効かず、新規 Codex session から有効になる前提で検証する。

Ownership

repo 管理対象
dotfiles tmux / fish wrapper、pane 表示、window scope helper、内部 transport helper、isolated tmux test。
claude.codex Codex config、writable_roots、global hooks、Codex skill、agmsg skill 配布、delivery policy。

Failure Modes

状況 扱い
tmux 外で起動 自動 join しない。manual team または no-op。
agmsg 未導入 明確な error を出す。自動 install はしない。
Codex writable root 不足 claude.codex の管理元 config を直し、新規 session で確認する。
worker が返信しない controller は timeout として扱い、未返信のままユーザーへ報告する。
Codex Stop hook が自分の pane identity を確定できない inbox を読まず fail-open する。複数候補の先頭を選んではならない。
target 以外の agent が message を読もうとした message は未読のまま残す。別 agent として request を処理してはならない。
reply は作られたが controller が回収していない controller は history / inbox で reply_to 宛の unread reply を確認し、回収結果をユーザーへ統合報告する。
closed pane の identity が team config に残る presence は別設計。peer 選択時は現在 tmux pane に存在するものを優先する。

Verification Plan

Transport checks

これは補助検証であり、UX 完了条件ではない。

  • window scope team が生成される。
  • AI pane に controller1 / worker1 / worker2 が付く。
  • pane title / sidebar に display identity と unread summary が出る。
  • pane 指定が active identity に解決される。
  • 別 window の team へ届かない。

UX E2E acceptance

ID 条件 証拠
AC-1 ユーザーが controller に自然文で worker 委譲を依頼できる。 操作ログに helper 直接実行がない。
AC-2 controller が peer を解決し structured request を内部送信する。 agmsg history に type / reply_to / expected_output / constraints が残る。
AC-3 worker が request として認識し scope 内で処理する。 worker の response に request id と constraints 遵守が含まれる。
AC-4 reply が controller に戻る。 reply_to 宛の message と controller inbox 表示。
AC-4.1 controller が worker 宛 request を自分で読まない。 Stop hook の identity が未確定の場合は read_at が付かず、worker の処理または timeout まで未読で残る。
AC-4.2 Codex worker 宛 request は即時処理を約束せず tmux 上に unread 通知される。 pane title / sidebar に worker1 !1 from controller1 相当が出て、通知表示だけでは read_at が付かない。
AC-5 controller がユーザー向けに統合報告する。 最終報告に findings / uncertainty / next action が含まれる。

作業計画

実装はこの順で進める。各フェーズは、次のフェーズに進む前にゲートを満たす必要がある。 transport check は補助であり、完了判定は常に UX E2E acceptance に置く。

Phase 作業内容 ゲート 完了条件
0. 設計整理 この HTML を設計の基準資料にし、agmsg 関連の Markdown 設計書を撤去する。 Markdown 側に別の成功条件や helper 直叩き手順が残っていない。 参照先がこの HTML に統一され、HTML parser 検証が通る。
1. controller workflow 自然文依頼を受け、peer 解決、structured request 生成、内部送信、状態観察、返信回収、統合報告を行う agent-facing workflow を定義する。 ユーザー向け手順に helper command が出ない。 controller が「1:2 に依頼して」を内部 transport に変換する手順が skill / rule に書かれている。
2. worker workflow worker が peer request を認識し、scope / constraints / expected_output を守って処理し、reply を返す rule を定義する。 peer request がユーザー指示より上位になる設計になっていない。 worker の reply に request id、status、findings / uncertainty / next_action が含まれる。
3. message contract 実装 request / reply の生成、routing、history 確認、timeout 扱いを実装する。 raw message を実用 request として扱わない。 agmsg history に type / id / reply_to / expected_output / constraints が残る。
4. transport 調整 既存 helper を agent 内部 primitive として必要最小限だけ調整する。 transport helper の CLI 例がユーザー手順に昇格していない。 isolated tmux test は通るが、これ単体では完了扱いにしない。
5. 実用 E2E 検証 新規 Codex session 前提で、ユーザーが controller に自然文で依頼する流れだけを実測する。 操作ログに helper 直接実行がない。 AC-1 から AC-5 までが実測証拠付きで満たされる。
